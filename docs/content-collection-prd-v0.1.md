| 项目 | 内容 |
| --- | --- |
| 文档版本 | V0.1 |
| 文档状态 | 已通过产品评审，作为 UI 设计与技术方案输入基线 |
| 更新日期 | 2026-10-22 |
| 适用产品 | QqChannelDesk / QQ 频道发布台 |

| 不在本期范围 | 自动发布策略、账号矩阵、团队协作、登录态抓取、本地模型部署 |

## 1. 结论与取舍

### 1.1 产品结论

V0.1 应建设“统一来源管理 + 受控采集 + 规则优先解析 + AI 兜底 + 人工审核入库”的内容供给链路，而不是让 AI Agent 全权接管采集。

目标链路：

```text
手动触发 / 定时调度
        ↓
公开 HTTP(S) 获取
        ↓
来源识别与确定性规则解析
        ↓
去重、筛选、字段归一
        ↓
解析失败或低置信度时调用 AI
        ↓
生成待审候选内容
        ↓
人工审核、修订、确认授权
        ↓
素材库
        ↓
现有排期与发布链路
```

### 1.2 为什么不是“AI 万能采集器”

| 方案 | 优势 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| AI Agent 全权浏览并抓取 | 初期看似适配更多网站 | 行为不可预测、成本高、难审计、易受网页提示注入影响，无法解决登录、验证码、反爬和版权问题 | 不采用 |
| 纯规则采集 | 快速、稳定、成本低、可测试 | 页面结构变化后维护成本高，长尾来源覆盖不足 | 不作为唯一方案 |
| 规则优先，AI 兜底 | 大部分请求稳定可控，长尾页面可降级处理，成本和审计边界清楚 | 需要增加 AI 服务抽象、脱敏、提示词防护和成本控制 | 采用 |

AI 可以降低“页面结构变化”带来的解析维护成本，但不能消除访问限制、授权风险、内容真实性风险或平台规则风险。

### 1.3 不可突破的产品边界

1. 只采集公开 HTTP/HTTPS 内容，不注入 Cookie，不读取登录态，不绕过验证码、付费墙或反爬机制。
2. AI 不直接发布内容，不自动决定入素材库，不自动排期。
3. 所有来源默认只把内容送入收件箱，必须经过人工审核。
4. 未确认内容使用授权的来源，不得开启自动入素材库或自动排期。
5. AI 只基于页面可见内容提取、摘要和格式建议，不得编造事实、作者、发布时间或媒体来源。
6. 采集失败必须保留可解释的结果，不得静默丢弃。

## 2. 背景与现状

### 2.1 现状

当前项目已经具备以下基础能力：

- 内容收件箱支持输入单个公开网页 URL，使用通用 HTML 规则提取标题和正文。
- TG 采集支持临时读取公开频道、关键词过滤、预览和人工入库。
- TG 定时采集支持 Cron、水位、去重、失败重试、取消、历史和账号隔离。
- 内容收件箱已有“待处理、保留、忽略、已入素材库”状态。
- 素材库与发布计划已经存在，手工发布和计划发布复用同一执行链路。
- 公开网页请求已有超时、重定向、大小限制和本机/私有地址拦截。

### 2.2 主要缺口

| 缺口 | 当前表现 | 用户影响 |
| --- | --- | --- |
| 来源没有独立对象 | 用户只能临时粘贴链接，TG 定时配置又是另一套模型 | 无法统一管理来源、频率、健康和授权状态 |
| 来源类型过少 | 主要依赖单页通用解析和 TG 定时 | 运营者不知道还能采什么，也难以持续供给内容 |
| 解析失败不可恢复 | 标题和正文都为空时直接失败 | 长尾站点无法使用，规则维护成本高 |
| 收件箱信息不完整 | 列表、预览、编辑混在双栏中 | 审核效率低，无法快速比较原文与 AI 候选稿 |
| 结果分类过粗 | 成功、失败、部分成功、AI 降级缺少统一口径 | 无法判断来源是否健康，也无法定位质量问题 |
| 来源健康不可见 | 缺少最近尝试、最近成功、连续失败、下次运行 | 用户只能在执行失败后排查 |
| 授权状态不可追踪 | 只有通用免责声明 | 无法证明具体来源已由用户确认使用范围 |

本次 V0.1 不执行真实登录、真实频道同步、真实采集或真实发布，只定义产品方案。

## 3. 目标用户与场景

### 3.1 目标用户

| 用户 | 特征 | 核心诉求 |
| --- | --- | --- |
| 单人频道运营者 | 管理 1 至 3 个 QQ 频道，内容主要靠手工寻找和搬运 | 用更低成本获得稳定内容供给，减少逐条复制粘贴 |
| 小型内容团队编辑 | 1 至 5 人协作，但当前产品仍为单机单账号 | 快速发现、筛选、改写和审核候选内容 |
| 垂直内容策展者 | 游戏、ACG、科技、活动、本地资讯等垂直领域 | 持续跟踪少量高质量官方来源，避免平台热点搬运风险 |
| 多频道管理者 | 同一批内容需要分发到多个频道，当前以人工管理为主 | 未来复用来源和素材，但本期只做单账号基础能力 |

### 3.2 非目标用户

- 需要批量控制大量账号、规避平台限制的账号农场。
- 需要抓取登录后内容、私人内容、付费内容或验证码页面的用户。
- 需要无授权搬运微信公众号、短视频平台或第三方创作者内容用于商业发布的用户。

### 3.3 核心场景

| 场景 | 用户任务 | 产品支持 |
| --- | --- | --- |
| 日常资讯补充 | 每天从官网公告、RSS 和技术博客获取新内容 | 定时采集后进入待审收件箱 |
| 垂直内容策展 | 持续跟踪 5 至 20 个高质量来源 | 来源管理、健康状态、关键词筛选 |
| TG 内容复用 | 从本人管理或已授权的公开 TG 频道获取内容 | 保留现有 TG 单次与定时采集，并统一进入来源和记录视图 |
| 临时发现 | 看到一篇公开文章，希望快速提取并转成 QQ 频道草稿 | 单链接采集 + AI 候选稿 |
| 异常恢复 | 某来源连续失败或页面改版 | 降级状态、明确错误、AI 兜底、人工再次解析 |

## 4. 产品目标与指标

### 4.1 产品目标

1. 让运营者不依赖平台专用爬虫规则，也能管理多种公开内容来源。
2. 建立稳定的内容供给：从来源发现、采集、去重、解析到收件箱可审。
3. 将页面结构变化导致的不可用问题，从“整条链路失败”降为“可解释的解析降级”。
4. 让 AI 提升审核效率，但不越过人工确认、版权确认和平台规则。
5. 为后续批量审核、来源模板、矩阵运营和多账号协作提供清晰的扩展点。

### 4.2 北极星指标

`每周被人工审核通过并成功进入素材库的有效内容数`

该指标同时反映采集量、来源质量、解析质量和审核价值，避免只追求抓取数量。

### 4.3 指标定义与目标初值

以下指标均为 V0.1 目标初值，正式上线前应使用脱敏后的真实使用数据校准。

| 指标 | 定义 | 目标初值 | 统计方式 |
| --- | --- | --- | --- |
| RSS/Atom 批次成功率 | 成功或降级成功的运行次数 / 应运行次数 | >= 95% | 排除用户暂停、取消和主动删除 |
| 网页栏目批次成功率 | 成功或降级成功的运行次数 / 应运行次数 | >= 90% | 先用 3 至 5 个代表来源校准 |
| 人工审核耗时 | 从内容进入待审到入素材库的平均时长 | 较当前流程降低 50% | 记录状态变更时间 |
| 重复入库率 | 同一账号内重复素材数 / 入库素材数 | < 1% | 以来源标识、URL 和内容指纹判定 |
| AI 兜底调用率 | 调用 AI 的内容数 / 成功获取内容数 | < 20% | 区分规则解析和 AI 解析 |
| AI 候选稿采纳率 | AI 参与后最终入素材库数 / AI 参与数 | >= 80% | 仅统计用户实际审核内容 |
| 定时任务启动延迟 | 计划时间到实际开始时间 | 95% 在 5 分钟内 | 不含程序未运行时段 |
| 未授权自动发布次数 | 未完成授权确认却自动发布的次数 | 0 | 硬性红线 |
| 跨账号数据泄露次数 | 账号 A 读取到账号 B 来源、条目或记录 | 0 | 自动化隔离测试和审计 |

### 4.4 成功指标不包含

- 不以采集条目总量作为核心成功标准。
- 不把规则解析成功、AI 降级成功、部分成功、失败合并成一个“总成功率”。
- 不以 AI 调用次数增长作为智能化成果。

## 5. MVP 范围与优先级

### 5.1 P0：V0.1 必须完成

| 模块 | P0 能力 |
| --- | --- |
| 来源类型 | 公开单链接、RSS/Atom、公开网页栏目、TG 频道 |
| 来源管理 | 新增、编辑、启用、暂停、删除、手动采集、定时采集 |
| 来源识别 | 自动识别 RSS、网页栏目和 TG，识别失败时允许用户手动指定类型 |
| 来源试采 | 保存前预览最多 10 至 20 条候选内容，试采不写入收件箱 |
| 统一收件箱 | 待审、保留、忽略、重复、已入素材库 |
| 内容审核 | 原文与 AI 候选稿对照、编辑标题和正文、添加标签、确认授权、入素材库 |
| 规则解析 | 标题、正文、发布时间、作者、主图 URL、原文链接、来源域 |
| AI 兜底 | 规则失败或低置信度时提取结构化字段并生成 QQ 频道候选稿 |
| 去重 | 来源条目 ID、规范化 URL、内容指纹三级去重 |
| 运行记录 | 最近尝试、最近成功、下次运行、状态、数量、失败原因 |
| 异常处理 | 超时、HTTP 错误、403、404、429、解析失败、AI 失败的分类展示 |
| 安全 | 公开地址校验、账号隔离、AI 内容脱敏、API Key 不落明文 |
| 兼容 | 保留现有 TG 单次采集、TG 定时采集、历史、重试、媒体入库行为 |

### 5.2 P1：验证 P0 后迭代

- 批量公开链接采集。
- 自定义 CSS 选择器、站点地图、公开 JSON/API 来源。
- AI 辅助生成来源规则建议，但必须由用户确认后启用。
- 批量审核、批量保留、批量忽略和批量入素材库。
- AI 分类、标签建议、相似内容聚合和选题热度提示。
- 视频和更多媒体类型的统一候选与授权确认。
- 经用户显式授权且来源满足条件的“自动入素材库”。

### 5.3 P2：中长期能力

- 多频道矩阵和团队协作。
- 跨来源专题聚合、内容日历和选题池。
- 在线大模型多供应商容灾、按任务路由和内容安全增强。
- 语义去重和跨语言内容适配。
- 来源模板市场或可导出的来源配置。

### 5.4 明确不做

- 登录态抓取、Cookie 注入、验证码识别、反爬绕过。
- 无授权的批量搬运、洗稿、伪原创和自动发布。
- AI 自主操作浏览器完成登录、点击付费墙或访问私域内容。
- 万能社交平台采集器。
- AI 自动认定版权归属或代替用户承担授权责任。
- 本地模型部署、本地推理服务和面向本机模型端点的接入。

## 6. 来源策略

### 6.1 推荐的首批来源

| 来源 | 适用内容 | P0 支持方式 | 主要风险 | 优先级 |
| --- | --- | --- | --- | --- |
| RSS/Atom | 官方博客、科技媒体、公告聚合 | 订阅 Feed 并解析条目 | 源质量、版权和全文转载限制 | P0 |
| 官网公告页 | 游戏、赛事、品牌、产品更新 | 列表发现 + 详情页规则解析 + AI 兜底 | 页面结构变化、访问频率 | P0 |
| 公开 TG 频道 | 已获授权的频道内容 | 保留现有 TG 采集能力 | 授权、媒体版权、访问稳定性 | P0 |
| 公开单链接 | 编辑临时发现的一篇文章 | 通用正文提取 + AI 兜底 | 版权与页面可访问性 | P0 |
| 站点地图 | 结构稳定、文章量较大的网站 | Sitemap 增量发现 | 大量 URL 造成负载和噪声 | P1 |
| 公开 JSON/API | 有明确公开文档和授权的数据源 | 配置字段映射 | 接口变更、授权范围 | P1 |
| 批量公开链接 | 编辑已有链接清单 | 批量试采、排队和失败明细 | 误采、权限和版权 | P1 |

### 6.2 暂不做一等公民支持的平台

以下平台在 P0 不应承诺批量采集能力：

| 平台类型 | 原因 | 允许的替代方式 |
| --- | --- | --- |
| 微信公众号批量文章 | 无稳定公开订阅接口，页面访问和反爬策略多变，版权风险高 | 若用户有明确授权，仅支持逐条公开链接试采 |
| 抖音、快手 | 内容主要依赖登录态、客户端能力和专有接口 | 不做自动抓取，可手工准备获授权素材 |
| 小红书 | 登录、反爬和版权风险高 | 不做首页或账号批量抓取 |
| 知乎、微博等 | 登录态、动态渲染和平台规则复杂 | 优先使用用户自有授权内容或官方开放接口 |
| 第三方 RSSHub 公共实例 | 可用性不可控，部分路由涉及绕过限制 | 只接受用户自行提供且合规的 RSS 地址 |

### 6.3 适合 QQ 频道的来源组合

| 内容方向 | 推荐来源组合 | 适配建议 |
| --- | --- | --- |
| 游戏频道 | 官方版本公告、活动页、赛事日程、开发者博客 | 规范为“版本/活动/公告 + 时间 + 要点 + 原图” |
| ACG 与兴趣社区 | 官方活动页、版权方公告、公开 TG 频道、授权创作者 RSS | 保留出处，避免脱离上下文的截图和二创 |
| 科技与数码 | 厂商博客、产品公告、RSS、公开 changelog | 强调版本号和事实来源，禁止 AI 补写参数 |
| 本地生活与活动 | 政府/场馆/主办方公开公告、活动日历 | 重点校验时间、地点和变更状态 |
| 品牌与个人 IP | 自有网站、授权 RSS、授权 TG 频道 | 可形成品牌内容复用和固定栏目 |

来源选择原则不是“尽量覆盖所有平台”，而是“优先覆盖有稳定供给、可公开访问、可证明授权、可低成本维护的来源”。

## 7. 信息架构与页面要求

### 7.1 一级结构

内容采集工作区固定为三个页签：

```text
内容采集
├─ 收件箱
├─ 来源管理
└─ 采集记录
```

高级能力下沉：

- TG 单次采集进入“采集链接”对话框。
- TG 定时采集进入“来源管理”，以 TG 来源类型呈现。
- 代理池进入来源或系统高级设置，不再占据一级页签。
- AI 服务配置进入系统设置或内容采集高级设置。

### 7.2 收件箱

采用“审阅优先”的三栏布局：

| 区域 | 内容 | 交互 |
| --- | --- | --- |
| 左侧筛选 | 来源、待审状态、内容类型、解析方式、是否使用 AI、时间 | 单选或多选筛选，显示各类数量 |
| 中间队列 | 标题、来源、发布时间、入库时间、状态、解析方式、置信度 | 单行选择，支持搜索和分页，避免同时塞入编辑表单 |
| 右侧详情 | 原文预览、AI 候选稿、可编辑正文、媒体、授权确认、操作 | 默认先对照，再编辑，避免 AI 结果直接覆盖原文 |

右侧详情至少包含两个视图：

1. `原文`：标题、正文、作者、发布时间、原文链接、解析警告。
2. `候选稿`：QQ 频道标题、正文、标签、AI 使用标记、置信度、风险提示。

页面主操作：

- `采集链接`
- `新建来源`
- `再次解析`
- `保存修改`
- `保留`
- `忽略`
- `标记重复`
- `确认授权并加入素材库`

### 7.3 来源管理

来源管理采用“紧凑状态栏 + 来源表格 + 详情抽屉或右侧面板”：

| 区域 | 内容 |
| --- | --- |
| 顶部状态 | 启用来源数、今日待审数、异常来源数、今日采集成功数 |
| 来源表格 | 名称、类型、来源地址、频率、最近尝试、最近成功、下次运行、健康状态、待审数 |
| 行操作 | 立即采集、暂停/启用、编辑、试采、查看记录、删除 |
| 详情面板 | 授权确认、解析方式、最近错误、AI 兜底比例、内容产量和重复率 |

禁止把“新增来源”表单长期占据页面主体。新增、编辑和试采应使用独立对话框或明确的分步流程。

### 7.4 采集记录

采集记录按“批次”而不是按单条文章展示：

| 字段 | 说明 |
| --- | --- |
| 触发方式 | 手动、定时、重试 |
| 开始和结束时间 | 本地时间，保留耗时 |
| 运行结果 | 成功、降级成功、部分成功、失败、取消 |
| 数量统计 | 发现数、获取数、规则解析数、AI 兜底数、重复数、新增待审数、失败数 |
| 来源健康变化 | 例如从“正常”变为“连续失败” |
| 错误摘要 | 已脱敏、可操作，不展示完整 HTML 或异常堆栈 |
| 关联操作 | 查看条目、再次运行、暂停来源、复制脱敏诊断信息 |

### 7.5 界面适配约束

- 在 960px 最小窗口宽度下，不出现按钮文字覆盖、列内容互相遮挡或不可访问的主要操作。
- 长 URL、长标题和错误摘要必须截断或换行，并提供查看完整内容的入口。
- 表格列可调整，关键字段不能被永久隐藏。
- 动态状态不能改变工具栏和操作区尺寸。
- 用户可见文案保持中文，并沿用现有 WPF 紧凑桌面风格。

## 8. 新建与试采来源

### 8.1 流程

```text
选择来源类型或粘贴 URL
        ↓
地址与公开访问校验
        ↓
自动识别 RSS / 网页栏目 / 单页 / TG
        ↓
用户确认来源名称、频率、筛选和抓取上限
        ↓
执行试采，只预览，不写入收件箱
        ↓
预览字段、重复情况和权限提示
        ↓
用户确认内容使用授权
        ↓
保存来源，按设置决定是否立即执行首次正式采集
```

### 8.2 来源字段

| 字段 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| 来源名称 | 是 | 自动根据站点标题生成 | 可编辑，账号内不要求唯一 |
| 来源类型 | 是 | 自动识别 | 单页、RSS/Atom、网页栏目、TG |
| 入口 URL | 是 | 无 | 只允许公开 HTTP/HTTPS |
| 采集频率 | 是 | 每 60 分钟 | P0 预设：30 分钟、1 小时、6 小时、每天 |
| 启用状态 | 是 | 暂停 | 用户完成试采和授权确认后可启用 |
| 每次上限 | 是 | 20 | 单页为 1，RSS/栏目和 TG 为 1 至 20 |
| 包含词 | 否 | 空 | 命中任一关键词才保留 |
| 排除词 | 否 | 空 | 命中任一关键词即排除，优先级高于包含词 |
| 授权确认 | 是 | 未确认 | 记录确认时间和确认人，不保存外部凭证 |
| 首次采集策略 | 否 | 最新 20 条 | RSS/栏目允许“仅新增”与“先导入当前条目” |
| 媒体策略 | 否 | 只记录媒体 URL | 用户确认授权后才允许下载入库 |
| AI 兜底 | 是 | 开启 | 受全局 AI 配置和调用额度约束 |

### 8.3 试采规则

- 试采结果最多预览 20 条，不写入 `CollectedItems`。
- 试采必须显示规则解析或 AI 兜底的结果。
- 如果试采得到 0 条，但页面请求成功，应提示“页面可访问，但未识别到内容”，允许调整类型或再次解析。
- 试采不得自动下载媒体。
- 试采不得自动入素材库或自动排期。

### 8.4 频率与礼貌访问

- 普通网页栏目默认每 60 分钟采集一次，P0 最低允许 30 分钟。
- RSS 默认每 30 至 60 分钟采集一次。
- TG 保留现有 Cron、并发、水位和重试行为，避免破坏已有配置。
- 同一来源默认串行执行，不因多次手动点击产生重复并发任务。
- 请求应使用可识别的 User-Agent、条件请求头和超时，减少无效流量。
- 对连续失败或返回 429 的来源自动暂停或降频，不进行高频重试。

## 9. 采集执行流程

### 9.1 批次步骤

1. 调度器或用户触发采集，创建一次运行记录。
2. 校验来源是否启用、是否已确认授权、是否已在运行。
3. 发起公开 HTTP/HTTPS 请求，执行地址、重定向、内容大小和超时校验。
4. 识别来源类型并获取条目列表。
5. 对每个条目执行规则解析，提取标题、正文、作者、发布时间、媒体 URL 和原文链接。
6. 计算规范 URL 和内容指纹，执行账号内去重。
7. 应用包含词、排除词和每批上限。
8. 规则失败或置信度不足时调用 AI 兜底。
9. 写入待审收件箱，并保存来源、运行记录和解析依据。
10. 汇总成功、降级、部分成功和失败数量，更新来源健康状态。

### 9.2 批次结果分类

| 结果 | 定义 | 是否计为采集成功 | 后续动作 |
| --- | --- | --- | --- |
| 成功 | 规则解析正常完成，关键字段达到阈值 | 是 | 内容进入待审 |
| 降级成功 | 请求成功，规则失败或低置信度，AI 兜底后形成可用候选 | 是，但单独统计 | 内容进入待审并标记 AI |
| 部分成功 | 部分条目成功、部分条目失败 | 是，但单独统计 | 成功条目进入待审，失败条目保留原因 |
| 失败 | 请求、列表发现或全部条目均无法形成可用内容 | 否 | 记录错误，按策略重试或告警 |
| 取消 | 用户主动取消或程序退出 | 不计入成功或失败 | 保存已完成内容和取消原因 |

必须分别展示以上状态，禁止只显示一个笼统的成功率。

### 9.3 失败处理

| 错误类别 | 示例 | 自动重试 | 用户提示 |
| --- | --- | --- | --- |
| 网络或超时 | DNS、连接失败、请求超时 | 是，P0 最多 3 次 | 检查网络或稍后重试 |
| 暂时性服务错误 | HTTP 500、502、503 | 是，P0 最多 3 次 | 来源暂时不可用 |
| 限流 | HTTP 429 | 按 `Retry-After` 等待，不立即重试 | 来源已限流，已自动降频 |
| 无权限或被拦截 | HTTP 401、403、验证码页 | 否 | 仅支持公开页面，不提供绕过方案 |
| 页面不存在 | HTTP 404、410 | 否 | 检查地址或删除来源 |
| 解析失败 | 无标题、无正文、字段异常 | 先 AI 兜底，不直接重试请求 | 显示解析降级或需人工处理 |
| AI 失败 | 超时、额度不足、返回格式不合法 | 不重复无限调用 | 保留规则结果或最低可用摘要 |
| 数据错误 | URL 非法、来源已停用、账号不匹配 | 否 | 明确提示具体原因 |

TG 来源继续沿用现有的 8 次退避重试、水位保护和部分媒体成功规则，不因统一来源管理而退化。

### 9.4 并发与取消

- 全局普通公开来源默认并发 1，P0 最多允许并发 2。
- 同一来源不允许同时执行两个批次。
- TG 并发继续受现有“TG 定时采集并发”设置控制。
- 取消运行后，已经成功写入的待审内容保留，未完成条目标记为取消。
- 超时或结果不明确时不自动重复写入，避免同一内容多次进入收件箱。

## 10. AI 辅助设计

### 10.1 AI 职责

| 能力 | P0 | 说明 |
| --- | --- | --- |
| 正文和标题提取 | 是 | 在规则解析失败或低置信度时执行 |
| 作者与发布时间识别 | 是 | 只在页面有明确依据时输出，否则留空 |
| 原文链接与主图 URL 归一 | 是 | 只接受当前来源域或其可信媒体域 |
| QQ 频道候选稿整理 | 是 | 清理格式、压缩冗余、保留事实和出处 |
| 标签和内容类型建议 | 是 | 结果只作为建议 |
| 是否适合 QQ 频道发布 | 是 | 输出参考评分和理由，不自动废弃或发布 |
| 来源规则修复建议 | P1 | 只生成建议，用户确认后才应用 |
| 自动写新观点或补全事实 | 否 | 不允许编造 |
| 自动发布或自动排期 | 否 | 永不开放 |

### 10.2 触发策略

满足任一条件时调用 AI：

- 规则解析没有正文，或正文长度明显不足。
- 没有标题，且页面无法通过 `og:title`、`title`、`h1` 恢复。
- 列表发现置信度低于阈值。
- 文章页出现疑似登录、验证码、错误页或空壳结构。
- 用户手动点击“再次解析”。

默认不对每一条成功规则解析的内容调用 AI，以控制成本、延迟和数据外发范围。

### 10.3 输入和输出

AI 输入：

- 页面可见正文、标题候选和必要的结构摘要。
- 来源域名、来源类型和用户筛选条件。
- 不发送 Cookie、Token、授权码、完整本地路径或账号隐私信息。
- 单次输入设置字符上限，超出时保留标题、正文开头和结尾摘要。

AI 输出必须使用严格结构化 JSON：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `title` | string | 不得编造，长度受 QQ 频道标题限制 |
| `body` | string | 保留原文事实，去除导航和广告文本 |
| `summary` | string | 用于列表快速审阅 |
| `author` | string/null | 无依据时为空 |
| `publishedAt` | ISO 时间/null | 无依据时为空 |
| `mediaUrls` | string[] | 只接受 HTTP/HTTPS，限制数量和域名 |
| `tags` | string[] | 最多 8 个建议标签 |
| `qqFitScore` | number | 0 至 1，仅作参考 |
| `confidence` | number | 0 至 1，必须展示 |
| `riskFlags` | string[] | 版权、时效、敏感、事实待核对等提示 |
| `reason` | string | 简短说明解析依据 |

输出必须经过字段、长度、URL 和 Markdown/HTML 清洗校验。校验失败视为 AI 失败，不使用不可信输出。

### 10.4 原文与候选稿分离

- 系统必须保留规则或原始文本抽取结果，不允许 AI 直接覆盖原文。
- AI 输出保存为候选稿，并标记模型、时间、置信度和触发原因。
- 人工修改后保存为用户修订版，后续 AI 再次解析不得自动覆盖人工修改。
- 收件箱详情必须明确显示“原文”和“AI 候选稿”的来源差异。

### 10.5 提示注入防护

网页内容一律视为不可信数据：

- 提示词不得允许网页中的指令改变系统任务。
- AI 不拥有工具调用、文件访问、浏览器操作或发布权限。
- 输出只接受预定义 JSON 结构，拒绝任意脚本、HTML 和外部指令。
- AI 返回的链接必须经过协议、域名和公网地址校验。
- 发现页面要求忽略规则、泄露配置或执行外部命令时，记录为风险提示并不执行。

### 10.6 AI 配置与成本

- P0 支持一种可配置的在线 OpenAI 兼容接口，不内置平台密钥。
- 仅接受公网 HTTPS 在线模型服务，不接受本机、私有网络或本地模型端点。
- API Key 使用 Windows DPAPI 或系统凭据存储，不得写入明文设置文件或日志。
- 设置页显示 AI 是否启用、当前服务、最近调用、调用上限和失败次数。
- 支持每日调用次数上限和单次内容字符上限。
- 达到额度后停止 AI 兜底，规则解析继续工作，收件箱保留“AI 额度已用尽”状态。
- 首次启用第三方 AI 时，必须明确提示内容将发送到所配置的外部服务。

## 11. 收件箱审核与入库

### 11.1 内容状态

| 状态 | 含义 | 是否可入素材库 |
| --- | --- | --- |
| 待审 | 新采集，尚未做人工决定 | 是，完成编辑和授权确认后 |
| 保留 | 暂不处理，但避免被清理 | 是 |
| 忽略 | 明确不采用 | 否，可恢复为待审 |
| 重复 | 已确认为重复内容 | 否，除非人工恢复 |
| 已入素材库 | 已生成素材并写入来源关联 | 不再重复入库 |

采集运行状态和内容审核状态必须分开存储，不能用“失败”同时表示批次失败和文章被忽略。

### 11.2 状态流转

```text
待审 ──> 保留 ──> 已入素材库
  │        │
  ├──────> 忽略
  ├──────> 重复
  └──────> 已入素材库
```

规则：

- 忽略、重复和已入素材库不能自动转回待审。
- 用户手动恢复必须留下状态变更时间。
- 入素材库操作必须原子化，并写入来源关联。
- 同一采集条目不能重复生成两个素材。
- 入素材库前再次校验标题、正文、媒体、QQ 频道长度和授权确认。

### 11.3 授权确认

收件箱中必须显示来源授权状态：

| 状态 | 表现 | 可执行动作 |
| --- | --- | --- |
| 已确认 | 显示确认时间和范围 | 可入素材库、可进入现有发布流程 |
| 未确认 | 明确警示 | 可编辑、保留、忽略，不允许自动入素材库或排期 |
| 范围不明 | 需要用户选择用途 | 只允许人工审阅，不允许自动处理 |

授权确认只代表用户在产品内完成操作确认，不代表系统对版权作出法律判断。

### 11.4 去重

按以下优先级判定：

1. 来源提供的稳定条目 ID，例如 RSS GUID、TG 消息链接。
2. 规范化原文 URL。
3. 同一来源内的内容指纹，例如标题和正文摘要的哈希。
4. 跨来源相似标题和正文，只标记“疑似重复”，不自动删除。

规范化 URL 的规则：

- 协议和域名小写。
- 移除 URL 片段。
- 移除已知跟踪参数，例如 `utm_*`。
- 保留可能影响内容定位的查询参数。
- 不把含明显 Token、登录票据或临时签名的 URL 保存为来源地址。

### 11.5 批量能力

批量审核、批量忽略和批量入素材库属于 P1。P0 只允许安全、可逐条追溯的单条审核，避免一次误操作把大量未授权内容送入排期。

## 12. 来源健康、记录与异常

### 12.1 来源健康状态

| 健康状态 | 判定 | 用户动作 |
| --- | --- | --- |
| 未验证 | 新建但未完成试采 | 试采并确认 |
| 正常 | 最近一次成功或降级成功 | 无需处理 |
| 降级 | AI 兜底比例高、部分成功或字段质量下降 | 检查来源或解析配置 |
| 异常 | 最近一次批次失败 | 查看原因并手动重试 |
| 连续失败 | 连续 3 次批次失败 | 默认暂停调度，人工确认后恢复 |
| 已暂停 | 用户主动暂停或触发限流保护 | 恢复前检查来源 |

### 12.2 时间字段

- `最近尝试`：每次开始运行都更新。
- `最近成功`：只有成功或降级成功才更新。
- `下次运行`：根据频率和当前健康状态计算。
- 失败或取消不得覆盖上次成功时间。

### 12.3 记录保留

- P0 每个来源保留最近 500 次运行记录。
- 单条内容记录保留最近 90 天或用户主动清理。
- 已入素材库的来源关联不得因采集记录清理而丢失。
- 删除来源时，默认保留历史收件箱和已入素材库内容，只停止后续调度。

### 12.4 错误文案

错误信息必须可操作，例如：

- “该页面需要登录，当前仅支持公开页面。”
- “来源返回了验证码页面，请更换公开来源。”
- “页面可以打开，但没有识别到正文。已尝试 AI 解析，仍建议手动检查。”
- “来源请求过于频繁，将在 30 分钟后重试。”
- “AI 服务暂时不可用，已保留规则提取结果。”

不得把完整 HTML、请求头、Cookie、Token、异常堆栈或完整本地路径显示在收件箱或复制诊断信息中。

## 13. 数据模型与账号隔离

### 13.1 新增或扩展的数据对象

| 数据对象 | 用途 | 关键字段 |
| --- | --- | --- |
| `CollectionSources` | 来源配置和健康状态 | 名称、类型、入口 URL、频率、授权、解析方式、最近尝试/成功、下次运行、健康状态、软删除时间 |
| `CollectionRuns` | 每次采集批次 | 触发方式、开始/结束时间、结果分类、各类数量、错误代码和脱敏摘要 |
| `CollectedItems` 扩展 | 统一收件箱条目 | 来源 ID、来源条目 ID、规范 URL、原文、候选稿、作者、发布时间、媒体、解析方式、AI 置信度、风险标记 |
| `CollectionSourceClaims` | 来源条目到素材的防重复关联 | `AccountKey`、来源 ID、来源条目 ID、素材 ID |

### 13.2 账号隔离

- 所有来源、运行记录、采集条目、候选稿、授权确认和素材关联必须带 `AccountKey`。
- 查询和写入必须使用当前账号上下文，不能通过来源 ID 绕过账号条件。
- 未登录时不得展示其他账号的来源或收件箱数据。
- 旧数据中 `AccountKey` 为空的记录继续按现有兼容策略隐藏或隔离。
- 账号切换后，运行中的采集任务不能把结果写入新账号。

### 13.3 数据保存原则

- 保存来源 URL、原文链接、标题、正文、摘要和必要的媒体 URL。
- 不保存用户 Cookie、Authorization、Token、二维码或登录页面内容。
- 不保存完整媒体本地路径到发布记录或日志。
- 不默认保存完整原始 HTML，只在当前运行临时内存中处理。
- 数据库迁移必须幂等，不得删除表、重建数据库或覆盖用户数据。

### 13.4 与现有模型的兼容

- 现有 `CollectedItems` 中的标题和正文继续可读。
- 新增字段使用兼容迁移补齐默认值。
- 现有 TG 计划和历史需要能映射到统一来源视图，但迁移前后不能丢失水位、重试、分发规则和历史。
- 手工发布和计划发布继续复用现有 `IPublishExecutor` 与 `PublishExecutionService`，本 PRD 不改变发布执行路径。

## 14. 合规、版权与安全

### 14.1 硬约束

| 风险 | 产品控制 |
| --- | --- |
| 未授权转载 | 来源授权确认、收件箱默认待审、未确认不得自动入库或排期 |
| 登录态和凭证泄露 | 不读取 Cookie、不注入登录态、不保存授权链接和二维码 |
| 验证码与反爬 | 检测到即停止，不提供绕过入口 |
| 本机或内网攻击 | 只允许公网 HTTP/HTTPS，拦截本机、私有、链路本地地址和异常重定向 |
| 高频抓取 | 最低频率、串行执行、随机抖动、限流退避、条件请求 |
| 第三方 AI 数据外发 | 显式提示、最小化输入、脱敏、调用上限和可关闭 |
| 提示注入 | 网页内容视为不可信数据，AI 无工具权限，输出严格校验 |
| AI 编造 | 保留原文、展示置信度、限制为提取和格式建议、人工审核 |
| 账号数据串读 | 所有业务表带 `AccountKey`，写入和查询均强制隔离 |
| QQ 账号风险 | 采集不直接操作 QQ 账号；发布侧继续受发布策略和平台规则约束 |

### 14.2 平台规则提示

- 采集不等于获得转载授权。
- 即使页面可公开访问，也应遵守网站条款、robots 约束、版权许可和合理使用范围。
- 不应将同一批未授权内容高频分发到多个频道。
- AI 生成的标题和摘要仍需人工核对事实、时效和出处。
- 发布到 QQ 频道前，继续遵守现有内容规则、目标频道权限和发布频率限制。

## 16. 现有实现改造建议

| 现状 | V0.1 改造 | 风险控制 |
| --- | --- | --- |
