## 1. 结论与取舍

### 1.1 产品结论

V0.2 不应把资源继续投入到“覆盖尽可能多的采集平台”。频道主反馈表明，更高频、更基础的痛点是：

1. 内容能否提前准备、按本地时间可靠发布，并在执行前被完整检查。
2. 广告、垃圾评论和违规内容能否被发现、分级和快速处理。
3. 发布结果、失败原因和后台数据差异能否被解释。
4. 成员能否被检索和按明确规则处理，而不是依赖不透明的“账号权重”。

V0.2 的定位应从“采集与自动发帖工具”升级为：

> 面向 QQ 频道主和小型运营团队的受控内容运营台：统一采集、人工审核、发布前检查、定时发布、异常核实和治理待办都可追溯。

### 1.2 优先级取舍

| 方向 | 取舍 | 理由 |
| --- | --- | --- |
| 发布工作台与审核闸门 | V0.2 P0 | 频道主明确要求定时发布；官方 CLI 已支持发帖、改帖、删帖和移帖；现有项目已有排期执行链路，增量价值最高 |
| 激励计划达成助手 | V0.2 P0 轻量版 | 官方激励页存在明确的月度阈值和截止日期；P0 先做官方指标手动快照、差距计算和到期提醒，不依赖未确认的数据接口 |
| 评论治理队列 | P1 | 官方支持读取、评论、回复和删除，但误判与误删风险高；先做“发现 + 建议 + 人工确认”，不做全自动治理 |
| 成员管理与分层 | P1 首批 | 官方支持成员列表、昵称搜索、资料和单目标管理；但“活跃率”的统计口径及最后活跃字段未确认，先做目录、检索、受控操作，再做字段驱动的分层 |
| 数据看板 | P0 仅做工具内运营数据 | 官方仓库未确认提供频道流量、推荐、留存、收益或激励归因数据 |
| 更多采集平台 | 沿用 V0.1 的 P0 边界 | 平台登录、反爬、版权和规则失效问题不会因换采集器消失 |
| AI 自主运营 | 不做 | AI 可做分类、摘要、风险提示和草稿，不能自主发布、删帖或处罚成员 |

### 1.3 本轮建议拍板

1. V0.2 P0 聚焦“发布工作台 + 发布前检查”，复用现有 `IPublishExecutor` 和 `PublishExecutionService`，不另建发布路径。
2. 评论治理 P1 只提供只读扫描、风险标记、处理建议和人工确认；删除、回复和处罚必须逐次确认。
3. 不对外承诺频道流量、推荐量、留存、账号权重、收益或激励资格，除非后续官方接口明确返回对应字段。
4. “定时发布”在产品中只能表述为本地计划公开时间，不能暗示 QQ 频道原生倒计时或平台定时任务。
5. 激励计划先做 P0 轻量版：用户手动记录官方页面展示的统计口径和当前值，工具负责计算差距、提示数据过期和生成真实运营动作清单，不自动刷访问时长、不模拟成员活跃、不预测结算金额。

- 评论按主题编码，一条评论可以同时命中多个主题，因此主题数量之和大于 156。
- 只保留聚合结论和改写后的需求描述，不复制用户昵称、头像、账号或其他个人信息。
- 156 条不是 281 条的全量样本，也不是 QQ 频道主的统计抽样，不能据此推导总体比例。
- 官方仓库说明的是 CLI 当前能力，不代表频道后台、移动端或未来版本的全部能力。
- 任何涉及真实账号的读写操作，都必须在使用本人管理的测试频道时另行验证。

## 3. 目标用户、场景与成功指标

### 3.1 目标用户

| 用户 | 典型情况 | 核心任务 | 当前痛点 |
| --- | --- | --- | --- |
| 频道主 | 管理 1 至 3 个频道，亲自决定内容和规则 | 保持稳定更新、处理违规、观察社区状态 | 时间碎片化，缺少统一待办和可解释结果 |
| 小型内容团队编辑 | 1 至 5 人，轮流值班 | 提前备稿、审核、按窗口发布 | 模板不统一、交接依赖口头说明、误发成本高 |
| 频道管理员 | 负责评论、成员和活动执行 | 快速发现广告和风险内容，按权限处理 | 缺少队列和审计记录，容易漏看或误操作 |
| 多频道运营者 | 同时维护少量关联频道 | 复用素材、分别控制时间与版块 | 频道身份、受众和规则不同，直接群发风险高 |

### 3.2 核心场景

| 场景 | 用户任务 | V0.2 产品支持 |
| --- | --- | --- |
| 提前备稿 | 白天完成内容，晚上或次日指定时间公开 | 草稿、审核、计划时间、暂停、取消和发布前检查 |
| 活动发布 | 按固定模板准备标题、正文、时间、链接和必要媒体 | 帖子模板、必填项检查、长度和媒体限制提示 |
| 异常恢复 | 计划逾期、CLI 超时或结果不确定 | 显示待核实，不自动重试，提供频道核对步骤 |
| 评论治理 | 找出广告、辱骂、诈骗和无关内容 | 只读扫描、风险分级、处理建议、人工确认 |
| 成员处理 | 搜索成员、禁言、踢人或调整管理员 | P1 先做快照与检索，后续再评估受控操作 |
| 周度复盘 | 判断内容是否按计划完成、失败集中在哪里 | 工具内任务指标、失败分类和来源产出质量 |
| 激励达成 | 在月度截止日前判断哪些官方条件未达标，确定优先动作 | 官方指标快照、差距计算、剩余天数、数据过期提醒和真实运营动作清单 |
| 成员结构诊断 | 几万人频道中找出可管理的成员群体，判断是成员规模问题还是内容互动问题 | 成员目录、搜索、角色与状态筛选、可选分页快照；没有官方活跃字段时不推断个人活跃 |

### 3.3 北极星指标

`每周经人工审核并按本地计划时间成功发布的内容数`

该指标同时要求“内容经过审核”和“发布链路可靠”，避免只统计抓取量、排期量或实际发帖量。

### 3.4 衡量指标

以下为目标初值，需在内测两周后用脱敏数据校准。

| 指标 | 定义 | 目标初值 |
| --- | --- | --- |
| 计划发布成功率 | 成功发布数 / 到期且未主动取消的计划数 | >= 95% |
| 准点发布率 | 计划时间后 5 分钟内成功发布数 / 成功计划数 | >= 95% |
| 计划逾期率 | 超过计划时间 15 分钟仍未执行数 / 到期计划数 | < 2% |
| 待核实结果率 | 超时或结果不明确任务数 / 计划发布数 | < 1% |
| 发布前检查通过率 | 首次检查无阻断项素材数 / 进入检查素材数 | >= 85% |
| 发布返工率 | 检查被阻断后重新编辑的素材数 / 被阻断素材数 | 作为基线观察 |
| 激励快照更新率 | 每周至少更新一次官方指标且数据未过期的参与频道数 / 启用激励助手的频道数 | 由内测建立基线 |
| 激励补齐动作完成率 | 用户明确标记完成的建议动作数 / 到期建议动作数 | 由内测建立基线，不将其等同于官方达标率 |
| 内容有效入库率 | 审核通过入素材库数 / 收件箱新增数 | 由 V0.1 内测建立基线 |
| 评论待办处理时长 | 风险队列产生到人工处理完成的平均时长 | P1 建立基线 |
| 治理误报率 | 被人工判为无需处理的建议数 / 建议总数 | P1 目标 <= 15% |
| 未授权自动发布次数 | 未确认内容授权却进入自动发布的次数 | 0 |
| 跨账号数据泄露次数 | 账号 A 读到账号 B 业务数据的次数 | 0 |

## 4. 频道主需求提炼

### 4.1 主题分布

| 主题 | 提及评论数 | 需求摘要 | 对产品的影响 |
| --- | ---: | --- | --- |
| 评论与治理 | 48 | 广告、骚扰、诈骗和无关评论多；希望权限更细、删除更顺畅、处理原因更清楚 | 需要治理队列、风险提示和审计，不应默认全自动删除 |
| 成员与权限 | 46 | 查找成员、清理无效成员、召回旧成员、调整管理员和加入审核 | 先利用官方成员列表与搜索能力，禁止批量骚扰 |
| 数据、激励与归因 | 32 | 希望看懂增长、内容表现、规则变化和激励结果 | 项目只能先展示自身发布数据，不能伪造平台指标 |
| 发现与创作者 | 21 | 好内容难被发现，创作者与频道连接弱 | 主要属于平台侧；桌面端只能做发布和复盘辅助 |
| 发布与排期 | 20 | 想提前准备、定时公开、避免夜间打扰、统一模板 | V0.2 最明确的 P0 需求 |
| 身份与隐私 | 20 | 跨频道互动时的身份、帖子和隐私边界不透明 | 官方能力未确认，不能设计跨频道身份控制 |
| 客户端与体验 | 16 | 桌面端和移动端能力、状态不一致 | 工具应明确自身边界，避免承诺平台客户端的缺失功能 |

### 4.2 需求改写

| 编号 | 频道主诉求（聚合改写） | 产品判断 | 优先级 |
| --- | --- | --- | --- |
| ON-01 | 我想提前编辑好内容，在指定时间公开，避免半夜打扰成员 | 本地排期可以解决；需明确“本地计划公开时间” | P0 |
| ON-02 | 我想在发布前知道标题、正文、图片、视频、链接和版块是否有问题 | 现有硬校验可扩展为统一发布前检查 | P0 |
| ON-03 | 活动帖需要固定字段和统一格式，减少漏项和广告感 | 做可复用模板与必填项，不做平台原生定时能力 | P0 |
| ON-04 | 计划失败、后台显示滞后或结果不确定时，我需要知道下一步做什么 | 保留非自动重试规则，增加待核实队列和处理指引 | P0 |
| ON-05 | 广告和垃圾评论太多，希望更快发现并处理 | 官方 CLI 可读取和删除评论；先做建议与人工确认 | P1 |
| ON-06 | 我希望能设置更细的评论权限 | 官方仓库尚未确认“仅成员可评论”配置，列为平台能力待验证 | 待验证 |
| ON-07 | 我想找出不活跃成员、清理或召回 | 成员列表可读，但“最后活跃”字段未确认，不能直接判断不活跃；先做目录与受控单目标管理 | P1 |
| ON-08 | 我想知道内容为什么表现不好，激励规则为什么变化 | 工具无法替代平台后台；提供自身发布数据，并允许手动记录官方激励指标与规则变化 | P1 |
| ON-09 | 我想在不同频道使用一致的内容，但不想混淆身份和语境 | 可复用素材与模板，不可承诺跨频道身份控制 | P2 |
| ON-10 | 我希望能发现更多合适的内容和创作者 | 采集侧按 V0.1 来源策略；平台推荐与创作者生态不由工具接管 | P2 |
| ON-11 | 我想在月度截止日前知道内容质量、成员活跃和频道主活跃是否达标，以及还差多少 | 官方页面已展示指标与阈值，但 CLI 未确认提供数据；先做手动快照、差距和提醒，再根据差距提供合规运营动作 | P0 轻量版 |
| ON-12 | 我的频道有几万人，但每天活跃的人很少，想快速查找成员、查看角色和禁言状态，并处理明确违规账号 | 官方支持成员目录、搜索、资料和单目标操作；不适合用全量枚举和批量踢人强行改善活跃率 | P1 |

### 4.3 明确不做成产品承诺的问题

- 不把“发得更多”解释为“流量更高”，也不提供所谓账号权重评分。
- 不根据评论关键词直接封禁、踢人或删帖。
- 不判断激励资格、收益金额或平台推荐结果。
- 不读取成员登录状态，不推断用户私域行为。
- 不批量私信“召回”成员，不自动加入或退出频道。
- 不承诺平台原生定时发布、定时删除或未来可见时间倒计时。
- 不通过模拟访问、自动停留、脚本互动、虚假账号或其他方式抬高成员活跃率和频道主访问时长。
- 不把工具内的动作完成情况包装成官方激励资格，也不保证用户最终获得激励金。

## 5. 官方能力与产品映射

### 5.1 已确认可用的官方能力

以下能力均以当前登录账号自身的频道权限为准，CLI 不会绕过权限。

| 领域 | 官方能力 | 产品可利用方式 | 优先级 |
| --- | --- | --- | --- |
| 发布 | 发帖、改帖、删帖、移帖 | 发布工作台、发布后修正、异常处理 | P0/P1 |
| 内容格式 | 短贴、长贴、Markdown、图片、视频、内联链接、@用户 | 发布前格式检查、链接归一、模板 | P0 |
| 帖子读取 | 帖子列表、详情、版块时间线、频道内搜索 | 发布结果核对、治理候选发现 | P0/P1 |
| 评论 | 读取评论/回复、发表评论、回复、删除评论/回复 | 评论治理队列、人工回复 | P1 |
| 帖子运营 | 点赞、加精、置顶、精华通知 | 发布后运营动作，高危动作需确认 | P1 |
| 成员读取 | 分页成员列表、昵称搜索、用户资料 | 成员目录、在线查询、可选本地快照 | P1 |
| 成员管理 | 禁言/解禁、踢人、批量操作、添加/移除管理员 | 产品只提供单目标、影响预览、二次确认和审计；不开放批量踢人 | P1 |
| 频道设置 | 频道信息、版块、加入方式、公告、频道私信 | 后续设置助手；不进 V0.2 P0 | P2 |
| 搜索 | 跨频道搜索、频道内搜帖 | 辅助找帖和审计，不承担推荐系统 | P2 |
| 通知 | `get-notices` 等通知读取 | 需先验证桌面端可用性；不得依赖 OpenClaw-only 订阅能力 | P1 调研 |

### 5.2 官方规则对发布设计的影响

| 规则 | 产品处理 |
| --- | --- |
| 短贴正文上限 1000 加权字，长贴上限 10000 加权字 | 按官方加权规则计算，不能只用字符串长度 |
| 中文和中文标点计 1 字，英文、数字和半角字符计 0.5 字 | 在编辑器和发布前检查中统一展示“官方加权字数” |
| 短贴最多 18 图、1 视频；长贴最多 50 图、5 视频 | 发布前检查按帖子类型动态校验 |
| 短贴图片和视频不能混用，长贴可以 | 选择媒体后立即提示并阻止无效组合 |
| 有标题即长贴，无标题即短贴 | UI 明确说明，不能把标题当成普通装饰字段 |
| 话题标签只支持短贴 | 长贴出现话题时阻断或要求移除 |
| 纯文本与 Markdown 互斥 | 编辑器必须有明确模式，切换时提示格式变化 |
| 裸 URL 不会自动变成可点击链接 | 检查裸 URL，提示转为内联链接 |
| 删除、禁言、踢人、移除管理员等需要 `--yes` | CLI 的 `--yes` 不能代替产品内人工确认 |
| 当前 CLI 未暴露未来定时发布 | 只显示本地计划时间，不声称平台已收到定时任务 |

### 5.3 尚未确认或不能承诺的能力

| 频道主需求 | 当前状态 | 产品响应 |
| --- | --- | --- |
| 平台原生定时公开和倒计时 | 官方文档未确认 | 仅做本地排期，不显示平台倒计时 |
| 频道流量、推荐量、留存、互动漏斗 | 官方 CLI 未确认 | 不建设虚假数据看板 |
| 激励资格、收益、账号权重 | 官方页面展示当前周期阈值和进度，但官方 CLI 未确认提供对应读取接口 | 允许用户手动录入本人可见的官方指标；工具只计算差距和提醒，不自动同步、不预测、不承诺 |
| 仅成员可评论等细分权限 | 官方文档未确认 | 标记为平台设置项，待真实权限验证 |
| 成员最后登录、长期不活跃 | 官方文档未确认 | 不自动标记“不活跃”，先确认返回字段 |
| 成员活跃率公式 | 官方激励页只展示比例，当前未确认分母、统计动作和刷新频率 | 不自行推算个人活跃；先用官方页面手动快照，待字段验证后再做群体分析 |
| 按频道区分的互动身份 | 官方文档未确认 | 不做多身份模拟或规避 |
| 定时删帖、自动清理 | 官方文档未确认 | 不做；删除必须人工触发 |
| 批量召回、群发私信 | 私信存在“对方未回复前只能发 1 条”等限制 | 不提供批量私信功能 |

## 7. V0.2 产品范围

| Markdown 模式 | 阻断/警告 | 按是否包含 Markdown 语法明确选择模式 |

#### 激励计划达成助手

官方激励页截图显示了一类典型月度条件：

| 条件 | 示例阈值 | 示例当前值 | 产品判断 |
| --- | --- | --- | --- |
| 内容质量 | 不鼓励帖子占比 <= 20% | 9.72% | 发帖前检查和内容复盘可以直接辅助 |
| 成员活跃 | 日均成员活跃率 >= 10% | 3.69% | 只能通过真实内容、活动和社区运营改善，禁止模拟活跃 |
| 频道主活跃 | 日均访问时长 >= 5 分钟 | 0.04 分钟 | 只能提醒频道主完成真实操作，禁止自动停留或脚本刷时长 |

P0 轻量版包含：

1. 新建激励周期：记录统计周期、截止时间、数据更新时间和数据来源说明。
2. 手动录入三项官方指标：阈值、当前值、是否达标；字段名称允许按官方页面调整，不把某一期规则写死。
3. 差距计算：显示百分点差距、时长差距和距离截止日的剩余天数，不预测最终能否达标。
4. 数据新鲜度提醒：超过用户设定的时限未更新时，标记“数据可能过期”，不继续展示为实时状态。
5. 可选金额记录：用户可自行记录预估激励金，但默认不采集、不分析、不上传，也不用于产品结论。
6. 历史快照：保留每次手动更新的指标和备注，方便复盘变化。
7. 真实动作清单：把未达标条件转为人工待办，例如使用发布前检查、准备讨论话题、回复评论、查看频道内容；动作完成只代表用户记录完成，不代表官方指标已达标。

建议动作必须遵守：

- 内容质量：优先使用官方规则检查和人工复核，不声称能准确复现平台“不鼓励内容”的内部判定。
- 成员活跃：可建议发布讨论题、活动公告、固定栏目或人工回复，但不得伪造互动、批量私信或诱导违规刷活跃。
- 频道主活跃：可提醒频道主进入频道完成查看、回复、治理和复盘，并记录其自述完成情况；不得自动打开页面、模拟点击或保持后台在线。
- 不提供“自动涨活跃”“自动挂时长”“保证达标”之类承诺。
- 截图导入和云 AI 解析不作为 P0 能力，避免昵称、头像、金额和指标不必要外发。若后续增加截图辅助，必须默认本地处理并提供明确确认。

### 7.2 P1：评论治理队列

P1 的目标是减少漏看和重复劳动，而不是让 AI 代替管理员做处罚。

| 能力 | 范围 |
| --- | --- |
| 新评论与回复扫描 | 只读取当前账号有权限访问的频道、版块和帖子 |
| 风险标记 | 广告、外链、诈骗、辱骂、重复刷屏、无关内容、待人工判断 |
| 上下文展示 | 展示评论、所在帖子、作者公开信息和命中原因 |
| 建议动作 | 忽略、观察、回复草稿、建议删除、建议禁言 |
| 人工确认 | 每次删除、回复、禁言都显示对象和影响范围 |
| 干跑模式 | 用户可先查看将执行的动作，不调用真实修改命令 |
| 审计 | 保存动作类型、时间、对象 ID、原因和结果，不保存完整凭证 |

硬约束：

- 不自动删除、自动禁言或自动踢人。
- 不根据单条关键词直接下结论；必须展示上下文和置信度。
- 被标记用户拥有申诉或人工复核入口。
- `--yes` 只能由确认后的操作生成，不能由后台定时任务默认追加。
- `get-notices` 和通知订阅是否能在桌面端独立使用，需在 P1 开始前验证；不得依赖 OpenClaw-only 能力。

### 7.3 P1：频道成员管理与活跃诊断

成员模块分为“成员目录”和“受控操作”两部分。目标是提高查找和处理效率，不是通过批量清理成员制造一个更好看的活跃率。

#### 成员目录

| 能力 | 范围 | 约束 |
| --- | --- | --- |
| 成员概览 | 频道成员总数、所有者/管理员/机器人/普通成员分类 | 只展示官方返回的计数，不推算活跃人数 |
| 昵称搜索 | 优先使用官方 `guild-member-search` 在线查询 | 不要求先全量下载几万名成员 |
| 分页目录 | 使用 `get-guild-member-list` 按官方分页令牌加载 | 不透明令牌必须原样传递，不猜测页码 |
| 条件筛选 | 角色、禁言状态、加入时间等官方实际返回字段 | 字段缺失时隐藏筛选，不能显示虚假数据 |
| 成员详情 | 昵称、角色、禁言状态、加入时间等最小必要资料 | 不展示 Cookie、Token、登录状态或私域信息 |
| 成员分层 | 管理员、机器人、新加入、已禁言、曾违规等明确分组 | “活跃/不活跃”只有在官方字段确认后才启用 |
| 可选快照 | 用户主动发起，分页保存并显示覆盖率 | 不支持默认后台全量同步；暂停、取消和续传必须可恢复 |
| 导出 | 用户主动导出当前可见字段 | 导出前提示包含成员公开资料，禁止默认含内部 ID |

大频道处理要求：

1. 默认采用在线搜索和按需翻页，避免每次进入页面都枚举整份成员列表。
2. 几万人频道发起快照前必须显示预计影响、暂停入口和“只读取，不修改成员”的说明。
3. 快照记录已完成页数、覆盖率、开始时间、最后更新时间和失败原因；部分完成时显示“不完整快照”。
4. 触发限流后停止自动翻页并保留进度，待用户稍后继续；不得无人值守地持续扫描。
5. 同一账号切换频道后，未完成快照不能继续写入新频道或新账号。

#### 活跃诊断

当前官方 CLI 已确认能读取成员和资料，但未确认返回“最后活跃”“最后登录”“最近发言”等字段，也未确认激励页成员活跃率的分母和统计动作。因此 P1 按以下边界设计：

- 不根据加入时间、禁言状态或昵称推测个人是否活跃。
- 不生成“僵尸粉分数”“账号权重”或“删除建议”等没有官方依据的结论。
- 不把“没有在本工具看到评论”等价为未活跃，成员可能只是浏览、签到或使用其他互动方式。
- 激励页的成员活跃率仍通过手动快照记录；成员模块只帮助分析成员规模和可观测互动覆盖情况。
- 若后续只读验证确认了官方活跃时间字段，才允许增加“最近活跃时间”筛选，并必须显示字段来源和更新时间。

假设官方活跃率的分母就是频道成员总数，那么以 1 万人频道为例：当前 3.69% 约等于 369 人，10% 目标约等于 1,000 人，每天仍需增加约 631 名活跃成员；3 万人频道则分别约为 1,107 人和 3,000 人。该计算只用于说明差距规模，不作为官方口径或达标预测。几万人频道仅靠成员管理通常无法解决，需要内容、话题、活动和成员结构共同改善。

在字段不足时，成员页只能提供以下可解释信息：

| 信息 | 产品表述 | 不允许的表述 |
| --- | --- | --- |
| 成员总数 | 官方返回的频道成员总数 | “真实活跃人数” |
| 加入时间 | 加入频道时间 | “沉默时长” |
| 禁言状态 | 当前禁言到期时间 | “风险账号” |
| 角色 | 所有者、管理员、机器人、普通成员 | “核心用户” |
| 本工具可观测互动 | 在已扫描评论/帖子范围内观察到的互动 | “频道内全部活跃行为” |

#### 受控成员操作

| 操作 | P1 能力 | 必须满足 |
| --- | --- | --- |
| 禁言/解禁 | 单个成员，显示到期时间和影响 | 选择明确对象、填写原因、二次确认 |
| 踢出成员 | 单个成员，默认不拉黑、不撤回消息 | 影响预览、原因、二次确认；拉黑和撤回消息必须分别确认 |
| 设置管理员 | 单个成员 | 显示权限提升影响，二次确认 |
| 移除管理员 | 单个成员 | 显示权限撤销影响，二次确认 |

操作规则：

- P1 不开放批量踢人、批量禁言和批量调整管理员，即使官方 CLI 支持批量参数。
- 执行前必须显示目标昵称、目标频道、动作、持续时间以及是否拉黑或撤回消息。
- CLI 的 `--yes` 只能由用户确认后的产品操作生成，不能由定时任务或默认配置自动添加。
- 优先使用 CLI 的 `--dry-run` 预览；预览结果不能当成已经执行。
- 执行超时或结果不明确时进入“待核实”，先重新读取成员列表或资料确认状态，不自动重试。
- 每次操作记录动作、目标内部引用、原因、确认时间、结果和脱敏错误。
- 不提供“清理不活跃成员以提高活跃率”的一键功能，也不把批量踢人包装成增长工具。

#### P1 流程

```text
选择频道
   ↓
按昵称搜索 / 按官方字段筛选
   ↓
查看成员详情与当前角色
   ↓
选择单目标操作
   ↓
权限检查 + 影响预览 + 干跑
   ↓
用户逐次确认
   ↓
执行并记录审计
   ↓
重新读取结果；不明确则进入待核实
```

### 7.4 P2：矩阵与平台生态能力

- 跨频道素材复用、频道级模板和品牌元数据。
- 多频道发布日历和只读聚合看板。
- 团队审批、角色权限和本地审计导出。
- 创作者、推荐和收益能力仅在官方提供明确接口和规则后立项；激励资格的自动同步、预测和结算解释也以官方接口为前提，V0.2 P0 只保留手动快照。
- 评论自动回复、成员召回和批量治理，仅在平台明确允许且产品完成风险评估后评估。

### 7.5 明确非目标

- 不建设养号、刷量、互赞、刷评论、虚假互动或规避风控能力。
- 不提供代理轮换、验证码绕过、登录态抓取或反检测。
- 不提供无上限群发、批量私信或骚扰式召回。
- 不提供批量踢人、批量禁言或“一键清理不活跃成员”来操纵活跃率。
- 不根据非官方字段生成个人活跃分、僵尸粉分或成员价值分。
- 不把 AI 判定包装成平台审核结论。
- 不提供“发布即涨粉”“保证不限流”“提高账号权重”等承诺。
- 不在未确认官方接口的情况下模拟频道后台私有请求。

## 8. 信息架构建议

V0.2 暂不新增过多一级导航，优先在现有“发布中心”和“运行总览”中形成闭环。

```text
发布中心
├─ 发布工作台
│  ├─ 待发布
│  ├─ 已排期
│  ├─ 逾期
│  └─ 待核实
├─ 素材库
└─ 发布计划执行器

运行总览
├─ 发布与审核指标
├─ 激励计划达成
├─ 任务运行环境
└─ 发布记录

社区治理（P1）
├─ 评论待办
├─ 处理记录
└─ 成员管理
   ├─ 成员目录
   ├─ 成员详情
   ├─ 可选快照
   └─ 操作记录
```

页面约束：

- 发布工作台沿用现有紧凑桌面布局，不采用网页式大标题和卡片套卡片。
- 阻断项和警告项必须使用不同状态，不能把所有检查结果显示成同一种“失败”。
- 计划时间旁明确显示时区，例如“2026-10-23 20:00（Asia/Shanghai，本地计划时间）”。
- 激励指标必须同时显示“当前值、目标值、差距、数据更新时间”，不能只显示一个达标或未达标标签。
- 激励页面的金额默认可隐藏，截图和官方指标不进入日志或诊断信息。
- 长标题、长 URL、错误摘要和成员昵称必须支持截断、换行或完整查看。
- 运行中、待核实和历史记录使用稳定列宽，动态状态不得推动工具栏位移。

## 9. 数据与账号隔离要求

新增业务数据必须按 `AccountKey` 隔离，数据库迁移必须幂等。

| 数据对象 | 用途 | 最小字段 |
| --- | --- | --- |
| `PublishPreflightRuns` | 一次发布前检查 | 素材 ID、规则版本、阻断数、警告数、检查时间、结果 |
| `PublishApprovals` | 人工审核记录 | 素材 ID、确认类型、确认时间、计划时间、用户确认摘要 |
| `IncentiveSnapshots` | 月度激励目标的手动快照 | 频道 ID、统计周期、指标定义、目标值、当前值、数据更新时间、来源说明 |
| `IncentiveActionItems` | 未达标指标的运营待办 | 快照 ID、建议动作、计划日期、人工完成状态、备注 |
| `ModerationCandidates` | 评论治理候选 | 频道/版块/帖子/评论 ID、风险类型、建议、置信度、状态 |
| `ModerationActions` | 人工处理审计 | 候选 ID、动作、确认时间、结果、脱敏错误 |
| `MemberSnapshots` | 一次可选成员快照 | 频道 ID、开始/完成时间、已完成页数、覆盖率、字段版本、状态 |
| `MemberSnapshotEntries` | 快照内最小成员摘要 | 快照 ID、内部成员引用、昵称快照、角色、加入时间、禁言状态、官方返回字段版本 |
| `MemberOperations` | 单目标成员操作审计 | 目标内部引用、动作、原因、影响摘要、确认时间、结果、脱敏错误 |

要求：

- 不保存 Cookie、Token、二维码、授权链接或登录页面内容。
- 日志不记录完整媒体路径、完整评论隐私内容或账号凭证。
- 账号切换后，后台任务不得把结果写入新账号。
- 发布审批和治理审计不得因素材或候选删除而失去追溯关系。
- 只读成员快照也要有明确保留期限和删除入口。
- 成员快照和导出默认只保存在本机，不进入日志、诊断包或云 AI 请求；导出前必须显示包含哪些公开字段。
- 成员操作记录不得保存凭证；目标内部引用只在当前账号作用域内有效，避免跨账号串用。
- 激励截图、头像、昵称和金额不进入日志、错误信息或诊断导出；金额字段必须可选且默认隐藏。
- 激励周期结束后，用户可删除快照；删除动作必须一次只作用于一个明确记录或用户明确选择的记录。

## 11. 风险与规避

| 风险 | 影响 | 规避设计 |
| --- | --- | --- |
| 把本地计划误解为平台原生定时 | 用户误以为关闭程序后仍会发布 | 全程标注“本地计划公开时间”，程序退出状态可见 |
| 加权字数或规则判断错误 | 合法内容被阻断或发布后才失败 | 集中规则服务、边界测试和 CLI 二次校验 |
| 发布前检查过于严格 | 用户绕过工具直接发布 | 只阻断官方硬限制和授权红线，其余为可确认警告 |
| AI 风险误判 | 正常评论被错误处理 | 只做建议、干跑、人工确认和误报复核 |
| 平台通知能力依赖 OpenClaw | 桌面端无法持续收到互动 | P1 启动前验证 `get-notices`；失败则不承诺实时通知 |
| 成员字段不足 | “不活跃成员”判断失真 | 字段白名单、缺失即隐藏，不使用推断值 |
| 活跃率口径不明 | 把成员总数当作活跃分母，或把浏览、发言、签到混为一谈 | 只采用官方说明；未确认前只展示官方页面手动快照，不计算个人活跃分 |
| 大频道全量同步 | 几万人分页耗时、触发限流、产生大量隐私数据 | 默认在线搜索；快照由用户主动发起，支持暂停、续传、覆盖率和保留期限 |
| 批量清理成员 | 为改善活跃率误踢真实成员，损害社区信任 | P1 只提供单目标操作，不开放批量踢人、批量禁言或一键清理 |
| 后台数据滞后 | 用户误判发布失败并重复发布 | 一律先展示待核实和核对路径，不自动重试 |
| 多频道误发 | 内容进入错误频道或版块 | 发布前二次展示目标，修改目标后重新检查 |
| 数据外发 | 页面或评论内容进入第三方 AI | 最小化输入、显式提示、在线 HTTPS 服务、调用限额 |
| 激励数据误导 | 用户把手动快照当成实时官方状态，或把工具建议当成达标承诺 | 显示数据更新时间、数据来源和“非实时同步”；不预测激励资格 |
| 诱导刷活跃 | 为完成成员活跃或频道主时长条件而模拟访问、虚假互动 | 不提供自动停留、脚本点击、批量互动；只记录真实运营动作 |
| 激励规则变化 | 把截图中的三项条件硬编码为所有频道、所有周期的固定规则 | 指标名称、阈值、周期和定义均可配置；版本变化时创建新快照，不覆盖历史 |

| A-08 | 平台没有可供工具读取的流量、推荐和激励归因接口 | 对照官方仓库、权限清单和真实后台能力确认 |
| A-09 | 频道主愿意每周手动更新 1 至 2 次官方激励指标 | 内测观察快照更新率和数据过期率 |
| A-10 | 手动快照和动作清单能帮助频道主更早识别未达标项，但不能直接提升官方指标 | 对使用前后行动完成情况做访谈，不将相关性表述为因果 |
| A-11 | 截图中的三项条件只代表该计划在当期的要求，不代表所有频道长期固定一致 | 收集不同频道、不同周期的官方页面并比对字段、阈值和统计口径 |
| A-12 | 成员活跃率的统计动作和分母可能与成员目录字段无关 | 对照官方规则、后台说明和只读测试数据确认，不自行建立个人活跃模型 |
| A-13 | 数万人频道的全量快照不适合默认后台同步 | 用测试频道评估分页耗时、限流次数和失败恢复；比较在线搜索与快照的使用频率 |

## 16. 本轮结论

V0.2 应优先把现有“素材库 + 排期 + CLI 发布”升级成可检查、可审批、可解释的发布工作台，并增加手动驱动的激励计划达成助手：帮助频道主看清官方阈值、当前差距和剩余时间，把差距转成真实的发布与社区运营待办。成员管理作为 P1 首批能力，先实现在线搜索、分页目录、成员详情和可选快照，再开放单目标禁言、踢人和管理员调整；不提供批量踢人换活跃率，也不在官方字段不足时推断个人活跃。评论与成员治理都必须分阶段、只读优先、人工确认、全程审计。频道流量、推荐、实时激励数据和身份隐私等平台侧需求应继续作为验证项，不能用产品文案、模拟活跃或推算数据替代官方能力。
